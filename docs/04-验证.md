# 04 软件验证

> 依据 02-工程意图 §5「完成判据」对 V1.0 进行验证。
> 验证不只判断"程序能否启动"，而是逐条对照需求与业务过程；本文档同时记录**没有做到**的部分（§5.2）。

## 1. 完成标准（Definition of Done）

**验收标准**回答"这个需求是否满足"（业务正确性）；**完成标准**回答"任何增量达到什么质量状态才算完成"（工程质量边界）。两者不可互相替代——代码能运行、页面能点，不等于达到了完成标准。

本版本对"完成"的约定：任一项工作只有**同时**满足以下各条才算完成。

| # | 完成条件 | 本版本核对方式 |
|---|---|---|
| 1 | 代码进入主分支 `main` | 全部改动以提交形式进入 main，工作区无未提交残留（`git status` 干净） |
| 2 | 关键测试通过 | `python -m unittest discover -s tests` → 30/30 通过 |
| 3 | 业务规则在服务端强制，不靠页面隐藏实现权限 | 权限装饰器 + 视图内归属校验；见 03-软件设计 §2 决策 5 |
| 4 | 文档与实现同步 | 需求 / 设计 / 实现 / 验证四方一致，调整登记于 03 §8 |
| 5 | 形成可运行版本 | `python run.py` 在约定环境启动，浏览器可走通主闭环 |
| 6 | 不引入敏感信息 | 仓库不含 `*.db`、`instance/`、密钥 Token（由 `.gitignore` 约束） |
| 7 | 可继续演化 | 关键数据不写死在代码中：演示数据由 `seed.py` 生成，代码内无硬编码业务数据 |

未达到上述条件的改动不进入主分支，也不计入本轮增量。满足全部条件的稳定节点以**版本标签 `v1.0`** 标识（见 README「Git 说明」），使后续反馈与缺陷报告能对应到确定的软件状态。

## 5. 验证与确认

### 5.1 两者回答的问题不同

| | 回答的问题 | 本版本所做的事 |
|---|---|---|
| **验证 Verification**（把软件做对） | 软件是否**满足已经定义的规格** | ✅ 30 个自动化用例逐条对照 FR 的业务规则与权限矩阵；13 步浏览器手工走查（§4） |
| **确认 Validation**（做的是对的） | 软件是否**解决了真实用户的问题** | ⚠ **未取得直接证据**，仅由需求分析阶段对业务问题的理解间接支撑 |

### 5.2 已知限制

诚实记录本版本**没有做到**的部分，避免把"测试通过"当成"问题已经解决"：

1. **无真实用户试用**：全部验证在开发环境完成，没有真实的学生或教师使用过。学生是否看得懂五种活动状态、教师是否愿意用系统名单代替群接龙，均无现场证据。
2. **无部署与运行反馈**：未部署到可访问环境，因此没有真实流量、并发、异常与数据增长的检验；SQLite 单文件 + 单进程开发服务器只适用于演示规模。
3. **确认（Validation）链条不完整**：需求来自对业务背景的分析，而非真实用户访谈。若"报名关系的确定性"不是用户最主要的痛点，本版本就可能没有解决最该解决的问题。
4. **自动化测试的边界**：测试只能证明"已设计的检查通过了"，不能证明需求边界本身正确。例如"三种收口下名单一律锁定"是设计决策，测试只证明实现与该决策一致，**不证明该决策优于其他方案**。
5. **未覆盖的工程环节**：无持续集成、无静态检查、无性能与安全专项测试；`SECRET_KEY` 使用开发默认值（可由环境变量覆盖），演示账号密码为公开的 `123456`。

以上限制不影响 02-工程意图 §5 完成判据的达成（判据针对"业务闭环是否成立"），但**限制了这些结论能外推到多大规模、多真实的场景**。后续阶段应优先补上真实使用反馈，再据此重排 01-需求分析 §5.2 的待办列表。

## 6. 结论（对照 02-工程意图 §5）

| 判据 | 达成情况 |
|---|---|

| 2. 规则生效（角色/截止/名额/去重/归属） | ✅ 30 个用例覆盖并全部通过 |
| 3. 页面可点 | ✅ 全部流程有页面入口与错误提示（§4 走查复核） |
| 4. 文档一致（需求↔设计↔实现↔验证） | 见 03 §8 调整记录与本文档的用例映射表 |

同时核对 §1 的 7 条**完成标准**：代码已全部进入主分支且工作区干净、30 个用例通过、规则均由服务端强制、四方文档一致、可运行版本形成、无敏感信息入库、关键数据未硬编码——**7/7 满足**，稳定节点已打标签 `v1.0`。

**结论：** 自动化测试 30/30 通过、种子冒烟通过、手工走查 13/13 通过（2026-09-18 复跑）。
V1.0 已达成 02-工程意图 §5 的全部完成判据：业务闭环成立、规则生效、页面可点、文档四方一致；工程质量上满足 §1 的全部完成标准。

**但需与 §5.1 的区分一并理解：** 上述结论属于**验证（Verification）**层面——软件确实做到了规格所要求的事；**确认（Validation）层面尚无证据**，即"做的是否是用户真正需要的东西"未经真实使用检验。§5.2 的已知限制是这一结论的适用边界。
