# 02 工程意图

> 校园活动管理系统 V1.0 · 工程意图（形成于需求分析之后、编码之前，作为设计/开发/验证的依据）

## 1. 为什么建设当前版本（V1.0）

学校的活动组织与参与目前停留在线下与群聊接龙阶段：活动信息分散、报名无记录、名单靠手工统计。V1.0 要回答的问题不是"能做多少功能"，而是"能否用一套小系统把 **发布—浏览—报名—名单** 这条活动业务主线真正跑通、跑稳"，让教师和学生第一次拥有关于"报名关系"的确定记录。

## 2. 当前版本主要解决什么问题

1. 学生需要一个**可靠的活动信息入口**：知道有什么活动、何时何地、还能不能报；
2. 教师需要一个**发布与收口工具**：发出去的活动能收回确定、排重的报名名单；
3. 双方都需要**规则一致的约束**：截止时间、名额上限、一人一次，由系统而不是接龙顺序来保证。

**不做的事同样重要**：不做通知渠道、不做管理审核、不做活动现场工具（签到等），避免把 V1.0 扩成"平台"。

## 3. 本轮准备完成的内容（范围）

见《01-需求分析》FR-1 ~ FR-11 与"候选但未纳入"清单。一句话概括：

> 一个三种角色（未登录/学生/教师）可用的 Web 系统：公开活动浏览；教师发布并管理自己活动的报名；学生在截止前报名与取消，规则（截止/名额/去重/身份）全部由服务端强制执行。

对应开发边界：

- 用户侧"注册/登录/角色"（FR-1）：注册选身份、密码哈希、登录会话与角色权限装饰器；
- 活动侧全部：发布、浏览、报名、取消报名、名单、结束、取消（FR-2 ~ FR-11，本次核心）。

## 4. 重要约束（实现必须遵守）

**业务与数据**
1. 报名/取消/状态变更的所有规则**必须在服务端校验**，页面只是入口；
2. 密码不落明文，使用单向哈希（werkzeug `generate_password_hash`）；
3. 一人一活动一条报名记录，由数据库 `UNIQUE(activity_id, student_id)` 兜底；
4. 时间统一存本机时间字符串 `YYYY-MM-DD HH:MM`，可比较可排序；"报名是否开放"等展示状态一律由时间推导，不落库（见设计 §4 决策 2 的理由）。

**技术**
5. 技术栈：Flask + SQLite，运行依赖仅 flask 一项；建库建表由代码在启动时按 DDL 自动完成；
6. 仓库内**不提交**任何 `*.db`、运行时目录、密钥 Token；SECRET_KEY 提供开发默认值并允许环境变量覆盖。

**过程**
7. 开发顺序遵守"需求 → 工程意图 → 设计 → 编码 → 验证"；若编码中发现原理解有问题，**先回查需求与工程意图，再决定改动**，不依据单次 AI 建议随意扩范围；
8. Git 随开发过程逐步提交，提交信息概括本次主要修改。

## 5. 完成判据（怎样算 V1.0 达到预期目标）

1. **闭环成立**：走完"教师登录发布活动 → 学生浏览看到 → 报名成功并可在列表中看到状态 → 教师查看名单"主线的每一步，无需人工干预数据库；
2. **规则生效**：用自动化测试覆盖并通过——非学生不能报名、重复报名被拒、截止后不能报名、满员不能报名、非发布教师不能看名单/结束/取消、取消后的活动不能报名（对应 FR-5/6/8/9/10）；
3. **页面可点**：全部业务流程在浏览器中可通过页面完成（含错误提示）；
4. **文档一致**：需求、设计、实现、验证四方一致，可互相追踪。
